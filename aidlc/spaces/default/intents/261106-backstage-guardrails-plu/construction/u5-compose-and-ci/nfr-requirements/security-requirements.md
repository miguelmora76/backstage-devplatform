# Security Requirements — u5-compose-and-ci

Sources: `requirements.md` (FR8.1, FR10.1, NFR5 audit integrity, NFR6), the functional design records: u5 has no `functional-spec.md` or `rules.md` of its own, because it adds no behavior and owns no entity or business rule (unit-of-work U5: "adds no behavior to the application"), so the rules it must not weaken are the finished units' (u2 BR rules on who may act, u4 BR4.1 to BR4.5 on settings and addresses), `contract-summary.md` (C3 sign-in and settings, the guardrails server address), the u4 security requirements and its hand-offs to u5 (`tech-stack-decisions.md`, "Hand-offs to u5": NFR2.3 end-to-end part, NFR5.6 origin check, NFR7.2 exit code), the u1 image rules (`packages/guardrails-server/Dockerfile`: non-root, one port, nothing written to disk), the phase rules for Construction (no secrets in code, validate input at boundaries, flag any bypass of authorization) and answers Q1 and Q2 in `nfr-requirements-questions.md`. Requirement IDs extend NFR5.

u5 adds no application behavior. Its security job is that the one-command run does not widen anything: no new way in, no port or secret that was not there, no container with more rights than it needs, and a pipeline that can read the code and nothing else. It also takes over the security checks u4 could not make without the running sample.

## Trust Boundaries

| Boundary | What crosses | Trusted? |
|---|---|---|
| Host to the app container (published port) | Browser traffic to one port, on the loopback address only | The only entry. Passwordless demo sign-in is on in this run (accepted risk of u2 NFR5.3) |
| App container to the guardrails server container | Plugin backend calls over the compose network | Not published to the host; reachable only from the compose network |
| App container to PostgreSQL | Plugin data, with the generated database login | Not published to the host; credentials from the environment only |
| Start script to the `.env` file | A generated throw-away database password | Created on first run, untracked, never printed |
| Pipeline to the repository | Code read with the default token | Read only; no secret, no push, no deploy |
| Test browser to the running sample | Synthetic data and demo tokens | Valid for that run only; reports and traces hold synthetic data |

## Requirements

| ID | Requirement | Measure and pass condition |
|---|---|---|
| NFR5.1 | The app's port is the only port the compose run publishes, and it is published on the loopback address only. | A test parses `compose.yaml` and finds exactly one `ports` entry in the whole file, bound to `127.0.0.1`; the compose job also reads `docker compose ps` of the running sample and finds only that one host port. The guardrails server and PostgreSQL appear with no `ports` entry. |
| NFR5.2 | No secret is committed, and the sample needs none from the pipeline. | A test reads `compose.yaml`, `.env.example`, the app image build file and the workflow, and finds every password, token or key only as a `${NAME}` substitution or empty; `.env` is listed in `.gitignore`. The one exemption is a named list in the test with two entries: the throw-away database login (`POSTGRES_PASSWORD: postgres` and the connection string built from it) that the two existing plugin jobs give their PostgreSQL service container; it is valid only inside the job, is documented as such in the workflow, and a new literal anywhere else fails. The start script writes a random password to `.env` on the first run only, never prints it, and leaves an existing `.env` unchanged. The workflow uses no repository secret (the test finds no `secrets.` reference). |
| NFR5.3 | Each container has the fewest rights it needs, and what it may write is a short, named list. | A test finds, for every service in `compose.yaml`, a non-root `user`, `cap_drop: [ALL]` and `security_opt: [no-new-privileges:true]`. The guardrails server also has `read_only: true` with no writable path (its image writes nothing, as its own Dockerfile says). The app writes in two places that Code Generation must name and keep to this list: `/tmp`, and the built frontend's static directory, because the app-backend plugin rewrites the frontend's JavaScript files at start to inject the runtime settings (checked in `plugin-app-backend`'s `injectConfigIntoStatic`). The app has `read_only: true` with those two paths covered (a tmpfs for `/tmp`, and a writable copy of the static directory made at start, or that directory left writable and owned by the non-root user); if neither works, the exception is written down with its reason and the test asserts the writable set equals the list. PostgreSQL runs as the `postgres` user with `read_only: true`, its data volume, and tmpfs for `/tmp` and `/var/run/postgresql` as the only writable paths, or the same kind of written exception. The pipeline's image checks find a non-root user and one exposed port for both images (u1's rule, extended to the app image). |
| NFR5.4 | Every image and every pipeline action is a fixed version. | A test finds each `image:` line and each `FROM` line in the repository's compose and image build files with an exact version tag (no `latest`, no bare major or major.minor such as `postgres:16`); where a `FROM` uses an `ARG` (as the server image does with `NODE_IMAGE`), the test reads the `ARG` default and checks that. It finds each workflow step `uses:` limited to GitHub's own `actions/*` at a major version, as the existing jobs do. The existing `postgres:16` lines of the two plugin jobs are changed to the same exact tag as compose (one value, chosen in Code Generation by checking the registry that day). |
| NFR5.5 | The demo sign-in is on only in the compose run, and the sample says so. | A test finds `GUARDRAILS_DEMO_SIGN_IN=true` set in `compose.yaml` and the shipped app settings still defaulting to false (u4 NFR5.2). The README states the passwordless risk and that the provider is replaced before any hosted use. The end-to-end run finds the user list open and the three sign-in choices shown. |
| NFR5.6 | The running backend accepts browser calls only from the app's own address and sends the content policy. (From u4 NFR5.6 and its hand-off.) | The end-to-end run sends a request with `Origin: http://localhost:7007` and finds `Access-Control-Allow-Origin` equal to it, then one with `Origin: https://example.org` and finds no `Access-Control-Allow-Origin`; it reads the `Content-Security-Policy` header of the page and finds `script-src` holding `'self'` and `'unsafe-eval'` (the reasoned exception of u4) and no `*` anywhere. |
| NFR5.7 | A token issued by the real sign-in works on the real plugin backend, and a call without one does not. (u4 hand-off for NFR2.3, end-to-end part.) | The end-to-end run signs in as each of the three demo users through `GET /api/auth/demo/start?userId=…`, calls the upgrade plan of a seeded service with that token and finds 200 with the seeded dependencies; the same call with no token, a malformed token and a token with one changed character is refused with 401 each. |
| NFR5.8 | Only the planned packages are added for the end-to-end work. | A script (the pattern of u4 NFR5.8) compares the declared dependencies of the new package with an allow-list kept beside it; the browser tool and its accessibility library are the only runtime additions. A package added on purpose edits the list in the same pull request. |
| NFR5.9 | The pipeline can read the code and nothing else. | A test of the workflow finds top-level `permissions: contents: read`, no job-level `permissions` that widen it, no `pull_request_target` trigger, and no step that logs in to a registry, pushes an image or deploys (no `docker push`, `docker login`, `deploy`). Every job, the existing ones included, has a `timeout-minutes` limit; u5 adds the missing limits to the existing jobs (a small edit, 15 minutes each, 25 for the compose job, see NFR1.3 in `tech-stack-decisions.md`). |
| NFR5.10 | Secrets and tokens do not reach logs, reports or uploaded files. | After the end-to-end run, the compose job searches `docker compose logs` and the browser report and traces for the generated database password and for every token it obtained, and finds none; the check fails the job on a hit. Uploaded files hold synthetic data only. |
| NFR5.11 | The audit log stays append-only in the running sample. (Inception NFR5, audit integrity, shown on the real stack.) | The end-to-end run proposes a change, reads its audit entry, approves it as another user, and finds the first entry unchanged (same fields and time). The plugin has one audit route, `GET /services/:service/audit`; the run sends `PUT`, `PATCH` and `DELETE` to it and to an audit entry's address, each with a valid demo token (without one the answer is 401, which proves nothing about the route), and finds each answered 404 or 405; it reads the entry count before and after and finds it equal. The PostgreSQL trigger test of u2 stays in its own job. |
| NFR5.12 | A missing server address stops the packaged app with a clear message instead of starting half-working. (u4 NFR7.2 hand-off.) | The compose job runs the built app image once with `docker run`, with every variable of the compose run except `GUARDRAILS_SERVER_URL`, and finds the container exited with a non-zero code within 60 seconds, its output containing `guardrails.server.url` (the settings key, which is what the backend prints; u4's `check:exit` asserts the same text), and its health check never healthy. This adds to u4's `check:exit`, which runs the source entry point on the host: this one runs the built image's entry point and its environment handling. |

## Accepted Risks

| Risk | Why accepted | Control |
|---|---|---|
| Passwordless demo sign-in: anyone who can open the page can become any demo user (u2 NFR5.3). | A demo needs no password; Contract Design Q1 chose it. | On only in compose; the port is on the loopback address only (NFR5.1); the README states the risk (NFR5.5). |
| The database password of the sample is a generated value in a local untracked file. | The database is not reachable from outside the compose network, and the sample holds invented data. | Random, never printed, not committed (NFR5.2). |
| Browser tool and accessibility library are third-party code run in the pipeline. | The checks cannot be made another way (Q1: A). | Pinned versions, an allow-list, a read-only token and no secret in the job (NFR5.8, NFR5.9). |
| Playwright's browser builds are downloaded in the job. | They come from the tool's own pinned release. | The version is pinned in the lock file; browsers are never part of an image. |

## Traceability

NFR5 (audit integrity) is shown on the running stack by NFR5.11, and the remaining NFR5.x items are the phase security rules for this unit (ports, secrets, rights, versions, sign-in scope, origin and content policy, token step, dependencies, pipeline rights, log hygiene, start failure). FR8.1 (one command, no manual step) is protected by NFR5.2 (the password is generated, not asked for); FR10.1 (a failing check fails the pull request) by NFR5.9 together with the summary job in `tech-stack-decisions.md`.
