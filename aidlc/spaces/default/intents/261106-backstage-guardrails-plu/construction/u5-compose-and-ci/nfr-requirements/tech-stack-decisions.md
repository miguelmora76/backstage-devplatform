# Tech Stack Decisions — u5-compose-and-ci

Sources: `requirements.md` (FR8.1, FR9.1, FR10.1, NFR1 to NFR7), `contract-summary.md` (the guardrails server address and readiness route), the u4 hand-offs to u5 (`tech-stack-decisions.md` of u4, "Hand-offs to u5"), the u4 infrastructure specification (environment variable names, the two settings files, the readiness route, the PostgreSQL volume), the u1 server image, the existing workflow `.github/workflows/ci.yml`, the team practices (tests first, 85% line coverage, Prettier and ESLint enforced in CI, local only, nothing deploys automatically) and answers Q1 and Q2 in `nfr-requirements-questions.md`. Requirement IDs extend NFR1 to NFR7; security items are in `security-requirements.md` (NFR5.1 to NFR5.12). Performance, scalability, reliability and observability are not separate documents for this packaging unit; their few items are rows below.

u5 is files for building and running, plus checks. The rule that matters most: it adds no behavior to the application, so every row is about running the sample or proving something about the running sample.

## Requirements

| ID | Requirement | Measure and pass condition |
|---|---|---|
| NFR1.1 | Each view shows its data within 5 seconds on the compose sample (Q2: A, blocks the pipeline). | The compose job loads each view 20 times in a row in a fresh browser context each time (empty cache): the sign-in choices, the catalog list, a seeded service's overview with its upgrade plan and failed runs, the changes list, a change detail and the audit log. A load is timed from navigation to the data-ready marker of that view (table below). Timing is blocking in Chrome only; Firefox runs the same loads once for the report and does not block. Before the timed loads the run creates a fixed set of three proposals so that the lists have rows. The 95th percentile (nearest rank: the 19th smallest of 20) of each view is at most 5000 ms, or the command exits non-zero. The one command `yarn e2e:timing` does this on a laptop and in the pipeline, so the job fails because of that exit code. The times are kept as a build artifact. |

Data-ready markers (a visible element that exists only once the view's data is rendered; the exact selectors are fixed in NFR Design and kept in one helper file):

| View | Marker |
|---|---|
| Sign-in choices | The three "Sign in as …" buttons are visible |
| Catalog list | The row of the seeded component `checkout-bridge` is visible, and the list shows six components |
| Service overview | The first seeded dependency row of the upgrade plan and the first seeded failed run are visible |
| Changes list | The three proposals created for the run are listed |
| Change detail | The change's title and its Approve and Reject buttons are visible |
| Audit log | The first page shows the entries of the three proposals |
| NFR1.2 | The compose run is ready quickly and fails clearly when it is not. | `docker compose up --wait` returns within 3 minutes once the images are built, which means all three containers report healthy; if not, the job prints each container's log and fails. |
| NFR1.3 | The whole compose job is bounded, with a time budget per phase. | `timeout-minutes: 25` on the compose job (raised from the 15 minutes first assumed, because the budget below adds up to more than 15) and 15 on every other job. Budget, a planning estimate to be measured in Code Generation: image builds 6 min, start 3, browser install 2, flows in two browsers 4, accessibility scans 1, timing (120 loads in Chrome) 5, header, token, log and missing-address checks 2, total 23. Each phase prints its time; if the measured total is over the limit, the limit and this budget are revised in the open in Code Generation, never silently. The other jobs run in parallel, so the compose job sets the pipeline's time. |
| NFR1.4 | The images are small enough to build and pull fast. | The app image is built from the output of u4's build only (no source, no test code, no development dependencies) and stays under 550 MB (raised from 500 MB; person-approved 2026-11-09); the job prints the size and fails above the limit. (The u1 server image keeps its own limits.) |
| NFR2.1 | Tests are written first, and the code u5 adds has at least 85% line coverage. (Team practice; inception NFR2.) | The code u5 adds that is not a container file or a workflow lives in one new package, `packages/e2e`, as TypeScript modules under `src/`: the start script logic, the `.env` creation, the compose-file and workflow checks, the percentile statistics, and the helpers of the end-to-end tests. They have unit tests that run without Docker, and they are the files the 85% floor counts. Excluded from the count, each with its reason: the `.mjs` entry files (a few lines that only call a module in `src/`, no logic), and the Playwright specs under `specs/` (they are tests, run against the live stack in the compose job, not unit-tested). The threshold of 85% line coverage is in the package's own test settings and is never lowered; a new CI job `e2e-unit` runs the package's tests with coverage, and the earlier floors (u1 to u4) stay as they are. |
| NFR2.2 | One command starts the whole sample with no other manual step (FR8.1). | From a clean checkout with Docker installed, `yarn compose:up` creates the missing `.env`, builds the images, starts the three containers, waits until they are healthy and prints the address. After it, the upgrade plan of a seeded service loads in the browser. The end-to-end run starts from exactly this command. A start script test covers: first run creates `.env`, a second run leaves it unchanged, a missing Docker command gives a plain message. |
| NFR2.3 | The compose file is checked without running Docker. | Unit tests read `compose.yaml` and assert the properties named in NFR5.1 to NFR5.5 and these: the app waits for the server and the database to be healthy; every service has a health check; the database has a named volume; the app's two base addresses are equal; the file contains no build step that needs a secret. Any violation fails. |
| NFR2.4 | The pipeline file is checked without running GitHub. | Unit tests read `.github/workflows/ci.yml` and assert NFR5.9 and these. The existing jobs stay as they are except three small edits that these checks need and that u5 makes: a time limit on every job, the exact PostgreSQL tag (NFR5.4), and the exemption of their throw-away database login (NFR5.2). Every job has a time limit; the new final job (`ci-ok`) lists every other job in `needs` and runs even when one fails, then fails itself when any needed job did not succeed, so the one required status of the repository covers every check (FR10.1); the workflow runs on pull requests and on pushes to `main`. |
| NFR2.5 | A failing check fails the pull request, and the setting that makes it block a merge is documented. (FR10.1.) | The README names the branch-protection setting (require the `ci-ok` status before merging), because a repository setting cannot be committed as code. A pull request with a deliberately failing check shows a failed status; this is shown once by a throw-away branch in Code Generation and recorded, or listed as open if the repository is not yet on GitHub. |
| NFR2.6 | A failure can be diagnosed from the pipeline's output. | On any failure the compose job prints `docker compose ps` and the logs of each service, and uploads the browser report and traces as a build artifact kept for 7 days. |
| NFR2.7 | The start is ordered and a failure is visible. | The app starts only after the guardrails server and PostgreSQL report healthy; no container restarts by itself (`restart: "no"`), so a crash shows. The app's health check uses the readiness route of u4, which stays not-200 until the plugin's migrations finish (u4 infrastructure specification). |
| NFR2.8 | Stopping and starting again is safe and says what it keeps. | `yarn compose:down` stops the containers and keeps the database volume; `yarn compose:reset` removes the volume as well and says so. The end-to-end run always starts from a reset so its results do not depend on an earlier run. |
| NFR3.1 | Every screen passes an accessibility scan at WCAG 2.1 AA in real browsers, including colour contrast. (u4 hand-off NFR3.4; inception NFR3.) | The end-to-end run scans, in Chrome and Firefox, the sign-in choices, the catalog list, a service overview with plan and failed runs, the changes list, a change detail and the audit log, with the rule sets `wcag2a`, `wcag2aa`, `wcag21a` and `wcag21aa`. Any violation fails; rules the scan cannot decide ("incomplete" results) are listed in the report and reviewed once in Code Generation. |
| NFR3.2 | The main task can be done with the keyboard alone in real browsers. (Inception NFR3.) | The end-to-end run signs in, proposes a change, signs in as another user, approves it with a reason and opens the audit log, using only key events (no pointer), in Chrome and Firefox; and checks that focus moves to the dialog or detail that opens and returns to a sensible element after it closes. |
| NFR3.3 | Every interactive element has an accessible name and role in the real accessibility tree. | The end-to-end run takes an accessibility-tree snapshot of each screen and finds no button, link, input or table without a name, and the sign-in choices named "Sign in as …" as u4 built them. |
| NFR3.4 | A pass with an actual screen reader is made once by a person, because no pipeline can run one. | The README holds a short checklist (sign in, read the upgrade plan, propose, approve, read the audit log) for VoiceOver with Chrome and NVDA with Firefox. It stays listed as an open item in the unit's code summary until the person has run it and noted the result. |
| NFR4.1 | The flows of FR1 to FR4 work in the current stable releases of Chrome and Firefox on desktop. (Inception NFR4.) | The end-to-end run executes the flows in both browsers: view the plan, propose an upgrade, view failed runs, propose a re-run, approve, reject (reason required), retry a failed change, and filter and page the audit log. Chrome is the Google Chrome stable channel as installed on the runner (it moves on its own, which is what "current stable" means); Firefox is the build that the pinned version of the browser tool ships, current stable at the pin date. The run uses a desktop window size of 1440 by 900 only. Both must pass. |
| NFR4.2 | The browser versions are known and kept current. | Each run prints the Chrome and Firefox versions it used into its report. Firefox moves only when the tool's pinned version is raised in a pull request (the README records the pin and the date checked). Chrome follows the runner: if a new Chrome release breaks a test, the pull request fails and that is a finding to fix, not a reason to pin Chrome. |
| NFR6.1 | Everything u5 adds is formatted and linted with Backstage's settings, enforced in CI. (Inception NFR6.) | The new package is covered by the same Prettier check as the repository and by `backstage-cli package lint`, added as a step of the existing `lint` and `typecheck` jobs; the compose file, the workflow, the image build file and the README pass `prettier --check`. A violation fails the pull request. |
| NFR7.1 | The compose run shows the same data every time. (Inception NFR7.) | The end-to-end run reads the seeded data through the real stack and compares the counts and names with the committed catalog (ten entities) and the default data set of u1 (seed 20261106); the seed is written as the literal 20261106 in `compose.yaml`, and the start script refuses, with a plain message, to run when `GUARDRAILS_SEED` is set to anything else in the environment or `.env` (one outcome: refused). A reset run and a second reset run give the same upgrade plan for the same service, compared byte for byte. |
| NFR7.2 | The audit and changes tables start empty after a reset, so every end-to-end run begins from the same state. | The run reads the changes list and the audit log of every seeded service after a reset and finds both empty. |

## Technology Decisions

| ID | Area | Decision | Reason |
|---|---|---|---|
| NFR2.9 | Container run | Docker Compose v2 (`compose.yaml` at the repository root), with `docker compose up --build --wait` behind the one command | The intent says docker compose; `--wait` gives health-based readiness. |
| NFR2.10 | Start command | A Node script (`.mjs`, like u4's `start-local`) behind `yarn compose:up`, `compose:down` and `compose:reset`; no shell script | Works the same on macOS, Linux and Windows; the logic is unit tested (NFR2.1). |
| NFR2.11 | App image | One image: u4's backend with the built frontend, made by a multi-stage build file at `packages/backend/Dockerfile`, built from the repository root like the server image; base `node:24.11.0-alpine3.22`, the same as u1's | One origin for the browser (the backend serves the frontend), the same base and rules as the existing image. |
| NFR2.12 | Database | `postgres` at an exact `16.x.y` or `16.x` tag chosen by checking the registry that day (the same value in compose and in the two existing plugin jobs, which today say `postgres:16`), a named volume, and u4's second settings file, so the PostgreSQL path is exercised for real | u4 left the live use of the PostgreSQL file to this unit; CI's plugin rule tests already use the same major version. |
| NFR2.13 | Server | The u1 image as it is, on the compose network only | No change to a finished unit. |
| NFR2.14 | Browser tests | Playwright (`@playwright/test`) with `@axe-core/playwright`, in a new workspace package, running Chrome (stable channel) and Firefox (Q1: A) | One tool covers both browsers, timing, keyboard events, header checks, the accessibility tree and an accessibility rule engine. |
| NFR2.15 | Helper code | TypeScript with Jest through Backstage's test runner for the code that has unit tests (the same toolchain as u1 to u4) | One toolchain, one coverage report format. |
| NFR2.16 | Pipeline | The existing GitHub Actions workflow, extended with: `app-image` (build the app image, not pushed; non-root and one-port checks as for the server image), `compose-e2e` (build, start, run the browser and header checks, the timing, the missing-address start, then stop), `compose-files` (the unit tests of NFR2.3 and NFR2.4, no Docker) and `ci-ok` (summary job, NFR2.4). Runner: `ubuntu-latest`, which has Docker and Compose. Node 24, as the other jobs. | The existing jobs stay; the new ones only add. |
| NFR2.17 | Nothing deployed | No registry login, no push, no deploy job (NFR5.9) | Team practice: nothing deploys automatically. |

New runtime packages (all are development dependencies of the new package, checked by the allow-list of NFR5.8): `@playwright/test`, `@axe-core/playwright`, `yaml` (already in the workspace, for reading the compose file and workflow in tests). The exact versions are chosen in Code Generation by checking the registry on that day and are then pinned. Nothing is added to the existing packages' dependencies.

## Hand-offs

From u4 and what u5 does with each: NFR1.3 of u4 becomes NFR1.1 here; NFR3.4 becomes NFR3.1 to NFR3.4; NFR4.1 becomes NFR4.1 and NFR4.2; NFR2.3 (end-to-end part) becomes NFR5.7; NFR5.6 becomes NFR5.6; NFR7.2 (exit code) becomes NFR5.12. To u6 (minikube, optional): the app image and its settings, the environment variable names and the end-to-end checks are reused; u6 does not change them.

## Alternatives Considered

| Choice | Alternative | Why not |
|---|---|---|
| Playwright for real-browser checks (Q1: A) | Cypress; Selenium | Cypress does not run Firefox and Chrome with the same keyboard and header checks as simply and has a heavier install; Selenium needs separate drivers and has no built-in timing or accessibility-tree support. Playwright was the person's choice. |
| Browser checks on every pull request (Q1: A) | A hand-run checklist only (Q1: B) | A regression would not fail a pull request; chosen against by the person. |
| Timing blocks the pull request (Q2: A) | Reports only (Q2: B) | A check that never blocks lets a slow view through; chosen by the person, with the 5-second limit generous for the small data set. If the shared runner proves too noisy, the finding is recorded and the choice reopened then. |
| Database password generated into an untracked `.env` | A fixed password in `compose.yaml` | A committed password would break the no-secret rule even for a local sample (NFR5.2). |
| One app image serving the frontend | Separate frontend and backend containers | Two origins would need the cross-origin settings in the shipped run and add a container for no gain. |
| A Node start script | A Makefile or a shell script | Not portable to Windows, and untestable with Jest. |
| A summary job as the single required status | Marking each job required | Every new job would need a repository setting change; one summary job needs it once (NFR2.4, NFR2.5). |
| Fresh browser context per timed load | One warm context | A warm cache hides the bundle download; the person's requirement says navigation to data shown. |
