# Infrastructure Specification — u5-compose-and-ci

Sources: `security-design.md` and `traceability.json` of this unit's NFR Design (the compose, image, start script, browser-check and pipeline designs), `nfr-requirements/security-requirements.md` and `tech-stack-decisions.md` (NFR1.1 to NFR7.2), `components.md` (u5 owns no component), `contract-summary.md` (the guardrails server address and readiness route), the u4 infrastructure specification (variable names, the two settings files, readiness route, PostgreSQL volume ownership), the u1 server image, and `infrastructure-design-questions.md`. There is no `functional-spec.md` for this unit (it adds no behavior). The earlier-stage names `performance-design`, `scalability-design`, `reliability-design`, `observability-design` and `logical-components` do not exist for this packaging unit; their few items are in `security-design.md` and `tech-stack-decisions.md`.

u5 provisions no cloud resource. This document says what exists on a developer machine and a GitHub-hosted runner when the sample runs, and which file creates it.

## Deployment

| Facet | Choice | Rationale |
|---|---|---|
| Compute model | Three containers started by Docker Compose v2: `app`, `guardrails-server`, `postgres` | Team practice: local only with docker compose (NFR2.9) |
| Networking | Two networks: `edge` (only `app`) and `internal` (`app`, `guardrails-server`, `postgres`; marked internal). One published port, `127.0.0.1:7007` to `app` | Server and database unreachable from the host (NFR5.1) |
| Storage | One named volume for PostgreSQL data; tmpfs for `/tmp` (app, database), `/var/run/postgresql` (database) and the frontend static directory (app); the server writes nothing | Read-only root file systems with named writable paths (NFR5.3) |
| Environments | One: local. CI uses the same files on a GitHub-hosted runner | Nothing deploys automatically (NFR2.17) |
| IaC approach | Plain files: `compose.yaml`, `packages/backend/Dockerfile`, `.dockerignore`, the start script; no cloud IaC | Nothing to provision in a cloud |
| Resource sizing | Memory limits: app 1 GB, server 256 MB, database 512 MB. `pids_limit`: app 256, server 128, database 128. tmpfs sizes (they count against the memory limit): app `/tmp` 64 MB, app static directory 64 MB, database `/tmp` 64 MB, database `/var/run/postgresql` 8 MB. No CPU limit is set (a local machine; a limit would only slow the timing check). The compose-file test asserts exactly these numbers. All are revised in Code Generation if a real run needs more, and the change is recorded | Stops a runaway container taking the machine (`infrastructure-design-questions.md`) |
| Start order | `postgres` and `guardrails-server` healthy, then `app`; `restart: "no"` | A failure stays visible (NFR2.7) |
| Start command | `yarn compose:up` (creates `.env.compose`, builds, starts, waits up to 180 s, prints the address); `compose:down`; `compose:reset` | One command, no manual step (NFR2.2, NFR2.8) |

## Infrastructure Services

| Service | Role | Configuration | Notes |
|---|---|---|---|
| `postgres` | database for `plugin-guardrails-backend`, reached through u4's `app-config.postgres.yaml` | Alpine image at an exact tag, user `70:70`, `cap_drop: [ALL]`, named volume, tmpfs `/tmp` and `/var/run/postgresql`, health check `pg_isready` | Written exception if it will not start under these rights (security design) |
| `guardrails-server` | the synthetic guardrails server (u1 image, unchanged) | Port 7007 inside the container, `GUARDRAILS_SEED=20261106`, `read_only: true`, no writable path, u1's own probe as health check | Unreachable from the host |
| `app` | Backstage backend serving the built frontend | Image from `packages/backend/Dockerfile`, working directory `/app`, start command in the security design, `read_only: true` with tmpfs for `/tmp` and the static directory, health check on the readiness route | The demo sign-in is on here only |

## Environment Variables of the Compose Run

Names are u4's (the infrastructure specification of u4 fixes them); u5 only sets values.

| Variable | Value in compose | Source |
|---|---|---|
| `GUARDRAILS_SERVER_URL` | `http://guardrails-server:7007` | `compose.yaml` |
| `GUARDRAILS_DEMO_SIGN_IN` | `true` | `compose.yaml`; README states the risk (NFR5.5) |
| `APP_BASE_URL`, `BACKEND_BASE_URL` | both `http://localhost:7007` (they must be equal in compose) | `compose.yaml` |
| `BACKEND_PORT` | `7007` | `compose.yaml` |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` | `postgres`, `5432`, `guardrails`, `guardrails` | `.env.compose` (not secret) |
| `POSTGRES_PASSWORD` | random value | `.env.compose`, generated by the start script, mode 0600, never printed |
| `GUARDRAILS_SEED` (server) | `20261106`, a literal | `compose.yaml`; the start script refuses any other value (NFR7.1) |

`.env.example` (u4) is not changed. `.env.compose` is added to `.gitignore` and, with all `.env*` files, to `.dockerignore`.

## Shared Infrastructure

|---|---|---|---|
| `.github/workflows/ci.yml` | u1-data-and-server (created), extended by each unit | u5 adds the compose jobs and three small edits | u5 does not change what the earlier jobs check |

| Guardrails server image | u1-data-and-server | u5 | Used as built |

## Hosting Later

Nothing in these files names a developer machine or a host. A hosted environment, or u6's minikube, takes the same two images, the settings files and the variable names; it must replace the passwordless demo sign-in and supply the database login from a secret store. No choice here blocks that (team practice: keep the ability to host later).
