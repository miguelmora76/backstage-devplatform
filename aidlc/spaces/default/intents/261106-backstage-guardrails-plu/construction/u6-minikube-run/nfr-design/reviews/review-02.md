> R-01 Reviewer note: "Server-down flow" now states find, then scale 0 plus `wait --for=delete pod/<name>`, then scale 1 plus `rollout status`, with the reason for each. The one gap left is that the unit test is described only as "a faked runner for both backends"; see the new Minor finding.

> R-02 Reviewer note: The "Probe timings" table gives startup, readiness and liveness period, timeout and failureThreshold for all three workloads. They match compose: server 12 retries and 3 s (`compose.yaml` healthcheck), app 30 retries and 5 s, postgres 20 retries and 5 s. Exec timeouts of 3 s or more cover `healthcheck.js`'s 2000 ms request (`TIMEOUT_MS`). The liveness route is named, with a TCP fallback. The manifest test asserts the minimums. One small inconsistency remains; see the new Minor finding.

> R-03 Reviewer note: The "Live exposure check" covers the non-loopback refusal, the 127.0.0.1 success and the closed port after `down`. "Image checks" covers non-root user and exactly one exposed port on the images the cluster runs. The NFR5.13 and NFR5.15 traceability rows now cite them.

> R-04 Reviewer note: "Target-cluster guard" runs before `minikube start` when the profile is already running, and again after it. Every later `kubectl` argument list carries `--context minikube`, and a unit test asserts this.

> R-05 Reviewer note: `wait-server` bounds each request with `AbortSignal.timeout(2000)`. Start step 6 reads `ps -p <pid> -o command=` and requires `kubectl`, `port-forward` and `guardrails-sample` before it trusts or kills a process.
