# Security Requirements — u6-minikube-run

Sources: u6 has no `functional-spec.md` or `rules.md` of its own, because it adds no behavior and owns no entity or business rule (unit-of-work U6), so the rules it must not weaken are the finished units' (u2 rules on who may act, u4 settings and address rules, u5 packaging rules); `requirements.md` (FR9.1, NFR5 audit integrity, NFR6), `contract-summary.md` (C3 settings and sign-in, C4 health routes), the u5 `security-requirements.md` and `tech-stack-decisions.md` (NFR5.1 to NFR5.12 and the hand-off "To u6": the app image, its settings, the environment variable names and the end-to-end checks are reused and not changed), the finished `compose.yaml` (the rights, writable paths and ports this unit must match), the unit description of U6 in `unit-of-work.md` (adds no behavior, owns no entity, may be dropped), the phase rules for Construction (no secrets in code, validate input at boundaries, flag any bypass of authorization) and answers Q1 to Q3 in `nfr-requirements-questions.md`. Requirement IDs extend NFR5 and continue after u5's NFR5.12, starting at NFR5.13.

u6 adds no application behavior. Its security job is that running on minikube does not widen anything compared with the compose run: no new way in, no secret in a file, no pod with more rights than its container had in compose, and no command that can touch a cluster other than the local minikube one. Every check the compose run already makes on the running application (origin, content policy, token step, append-only audit log) is reused as it is, because the application is the same image.

## Trust Boundaries

| Boundary | What crosses | Trusted? |
|---|---|---|
| Host to the app pod (port-forward) | Browser traffic to one port, on the loopback address only | The only entry. Passwordless demo sign-in is on in this run (accepted risk of u2 NFR5.3) |
| App pod to the guardrails server pod | Plugin backend calls over the cluster network | Reachable only through a cluster-internal service address |
| App pod to PostgreSQL | Plugin data, with the generated database login | Cluster-internal service address only; the login comes from a Kubernetes Secret |
| Start script to the cluster | Manifests, the generated Secret and image builds | Only the local minikube cluster; the script refuses any other cluster |
| Start script to the Secret | A generated throw-away database password | Created on the first run, never printed, never written to a tracked file |
| Pipeline to the repository | Code read with the default token | Read only; no secret, no push, no deploy |
| Pipeline to downloaded tools (minikube, kubectl) | Two program files fetched in the job | Exact version and a checked digest |

## Requirements

| ID | Requirement | Measure and pass condition |
|---|---|---|
| NFR5.13 | The only way into the sample from the host is the port-forward on the loopback address; nothing else is exposed outside the cluster. (Matches NFR5.1.) | A test reads every manifest under `k8s/` and finds no Service of type `NodePort` or `LoadBalancer`, no `Ingress`, and no `hostPort`, `hostNetwork` or `hostPID` in any pod. The guardrails server and PostgreSQL are Services of type `ClusterIP`. The start script test finds the port-forward started with the address `127.0.0.1` and finds a refusal when the local port is already taken. The live job finds that connecting to the machine's non-loopback address on port 7007 is refused. |
| NFR5.14 | No secret is committed, and the database password never appears in a command line, a log or a file in the repository. (Matches NFR5.2.) | A test reads `k8s/` and the start script and finds the password only as a `secretKeyRef` to the Secret by name; there is no `kind: Secret` with data, no `secretGenerator` with literals and no `.env`-style file under `k8s/`. The start script creates the Secret on the first run only, from a random value passed on standard input (never in the argument list, which the test asserts by inspecting the arguments of the call), never prints it, and leaves an existing Secret unchanged (three unit tests). After the live run the job searches the output of `kubectl logs` for every pod, the browser report and traces for the password and for every token it obtained, and fails on any hit. The workflow uses no repository secret (the compose-file test already searches for `secrets.`; it is extended to the new job). |
| NFR5.15 | Each pod has the fewest rights its container had in compose, written as pod settings. (Matches NFR5.3.) | A test finds, for every container in every workload: `runAsNonRoot: true` with the same user as in compose (1000 for the server and the app, 70 for PostgreSQL), `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `readOnlyRootFilesystem: true` and `seccompProfile.type: RuntimeDefault`; for every pod, `automountServiceAccountToken: false`; no `privileged`, no extra `capabilities.add`. The writable set of each container is exactly the compose list: server none; app `/tmp` and the frontend static directory (each an `emptyDir`, the second filled from the image's pristine copy before the backend starts, as in compose); PostgreSQL its data volume, `/tmp` and the socket directory. A test asserts the mounted volumes equal that list. Because a non-root container cannot write to a volume it does not own, each pod also sets `fsGroup` equal to its container's user (70 for PostgreSQL, 1000 for the server and the app), and the test finds it on every pod that mounts a PostgreSQL claim or an `emptyDir`, so the writable set is writable by that user and by no other. If a container cannot run with a setting, the exception is written next to the manifest with its reason and the test names it; no silent loosening. |
| NFR5.16 | Nothing outside one dedicated namespace is created or changed, and no cluster-wide right is needed. | A test finds that every namespaced object names the namespace `guardrails-sample` through the kustomization and that `k8s/` holds no `ClusterRole`, `ClusterRoleBinding`, `CustomResourceDefinition`, `PersistentVolume`, `StorageClass`, admission webhook, or any other cluster-scoped object. The namespace itself is created by the start script, and removing the sample removes it. Each workload uses a service account of its own with no role binding. |
| NFR5.17 | The start script can only act on the local minikube cluster. | Unit tests with a faked `kubectl` and `minikube` find that the script reads the current context first and refuses, with a plain message and no change made, when it is not the context named `minikube` or when the cluster address is not a local one (the check is done on the context name and on the `minikube` tool's own report, not on the address alone). The same refusal applies to `minikube:down`, so it can never delete the namespace of another cluster. |
| NFR5.18 | Every image, tool and pipeline action is a fixed version. (Matches NFR5.4.) | A test finds each `image:` in `k8s/` as an exact tag: PostgreSQL the same tag as `compose.yaml` and the two plugin jobs (one value, asserted equal across the three), and the two built images a fixed local tag (`local`, never `latest`) with `imagePullPolicy: Never`, so nothing is pulled in the cluster that was not built here. The workflow downloads minikube and kubectl at exact versions from their official release locations and checks each file against a SHA-256 value written beside the version; a mismatch fails the job. The job's `uses:` entries are limited to GitHub's own `actions/*` at a major version. A test checks all three. |
| NFR5.19 | The demo sign-in is on only in this run and the README says so. (Matches NFR5.5.) | A test finds `GUARDRAILS_DEMO_SIGN_IN` set to `true` only in the sample's ConfigMap, with the shipped app settings still defaulting to false (u4 NFR5.2). The README states the passwordless risk and that the provider is replaced before any hosted use. The live run finds the user list open and the three sign-in choices shown. |
| NFR5.20 | The running backend accepts browser calls only from the app's own address, sends the content policy, accepts a call only with a valid token, and keeps the audit log append-only. (Reuses NFR5.6, NFR5.7 and NFR5.11 of u5 with their assertions unchanged.) | The live job runs the same end-to-end specs as the compose job against `http://localhost:7007` through the port-forward (`E2E_BASE_URL`, with the two switches of NFR1.5 and NFR2.24 in `tech-stack-decisions.md`, neither of which touches a security assertion); the header checks, the three-user token step with the refused bad tokens and the PUT, PATCH and DELETE probes of the audit routes all pass. These specs are not copied: u6 runs them from `packages/e2e` as they are. |
| NFR5.21 | The pipeline job can read the code and nothing else. (Extends NFR5.9.) | A test of the workflow finds the new job under the same top-level `permissions: contents: read`, no job-level widening, no `pull_request_target` trigger, no registry login, no push, no deploy, no `sudo`-installed package beyond the two pinned tools, and a `timeout-minutes` on the job. The cluster runs on the runner with the Docker driver and is gone when the job ends. |
| NFR5.22 | A stop leaves nothing running that could expose the sample. | `yarn minikube:down` stops the port-forward process (found by the process id the start script wrote, never by name matching) and removes the namespace. A test with fakes finds both steps in that order, and finds that a stale process-id file whose process is not the port-forward is ignored rather than killed. The live job finds port 7007 closed after the stop. |

## Accepted Risks

| Risk | Why accepted | Control |
|---|---|---|
| Passwordless demo sign-in: anyone who can open the page can become any demo user (u2 NFR5.3). | A demo needs no password; Contract Design Q1 chose it. | On only in this sample; the entry is the loopback address only (NFR5.13); the README states the risk (NFR5.19). |
| No network policy between pods. | Default minikube has no network plugin that enforces them, so a policy object would look like protection and give none. | The server and the database are reachable by cluster-internal addresses only and there is no route from outside the cluster (NFR5.13); the document states the gap so that a hosted cluster adds policies. |
| The database password of the sample is a generated value held in a Kubernetes Secret, which is stored unencrypted in the local cluster. | The cluster is the person's own local one and the sample holds invented data. | Random, never printed, not committed (NFR5.14). |
| Two third-party programs (minikube and kubectl) run in the pipeline. | The live check cannot be made another way (Q3: B). | Exact versions, checked digests, a read-only token and no secret in the job (NFR5.18, NFR5.21). |
| Images are built inside the cluster's own image store with no scan. | Same base and build files as compose; nothing is pushed anywhere. | The build files are the ones u1 and u5 already check (non-root, one port); the job repeats those two checks on the images it built. |

## Traceability

NFR5 (audit integrity) is shown on the minikube run by NFR5.20, which re-runs the append-only check of u5 on the same image. The remaining NFR5.13 to NFR5.22 items are the phase security rules for this unit (exposure, secrets, pod rights, scope of changes, target cluster, versions, sign-in scope, pipeline rights, shutdown). FR9.1 (the same check as FR8.1 succeeds on minikube) is protected by NFR5.14 (the password is generated, not asked for) and NFR5.17 (the command cannot reach another cluster); FR10.1 by NFR5.21 together with the summary job in `tech-stack-decisions.md`.
