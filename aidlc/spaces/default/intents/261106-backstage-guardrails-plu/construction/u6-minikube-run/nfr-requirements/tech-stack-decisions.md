# Tech Stack Decisions — u6-minikube-run

Sources: `requirements.md` (FR9.1, FR8.1, FR10.1, NFR1 to NFR7), `contract-summary.md` (C3 settings, C4 health routes and the server address), the u5 `tech-stack-decisions.md` and `security-requirements.md` (including its hand-off "To u6"), the finished `compose.yaml`, `.github/workflows/ci.yml` and `packages/e2e` (the start script, the end-to-end specs and the `E2E_BASE_URL` setting), the unit description of U6 in `unit-of-work.md`, the team practices (tests first, 85% line coverage, Prettier and ESLint enforced in CI, local only, nothing deploys automatically) and answers Q1 to Q3 in `nfr-requirements-questions.md`. Requirement IDs extend NFR1 to NFR7; security items are in `security-requirements.md` (NFR5.13 to NFR5.22). Performance, scalability, reliability and observability are not separate documents for this packaging unit; their few items are rows below.

u6 is files for running on minikube, plus checks. The rule that matters most: it adds no behavior to the application and changes no finished unit, so every row is about running the sample on a cluster or proving something about it. The application image and its environment variable names are u5's, reused as they are; the end-to-end specs are u5's too, with two small default-preserving switches added (NFR1.5, NFR2.24).

## Requirements

| ID | Requirement | Measure and pass condition |
|---|---|---|
| NFR1.5 | The minikube sample shows the same data as compose within the same limit, but timing does not block there (Q3: B). | The live job runs the 20-load timing command (`yarn e2e:timing`) against the port-forward and keeps the numbers as a build artifact; the job does not fail on the 95th percentile. Today `specs/timing.spec.ts` asserts the 5000 ms limit unconditionally, so u6 adds one switch to it: the environment variable `E2E_TIMING_BLOCKING` (default `true`; the compose job leaves it unset and stays blocking, where inception NFR1 is measured). The minikube job sets it to `false`, and the spec then still measures, prints and writes every p95 but skips the assertion. A unit test of the small module that reads the switch covers both values and an invalid one (treated as `true`). On a laptop, `yarn e2e:timing` against minikube prints the same table. |
| NFR1.6 | The start is bounded and fails clearly. | `yarn minikube:up` returns within 5 minutes once the images are built, which means every workload reports ready and the app's readiness route answers through the port-forward; if not, it prints each pod's description and log and exits non-zero. The command prints the time of each phase (tool checks, image builds, apply, rollout, forward). |
| NFR1.7 | The whole live job is bounded, with a time budget per phase. | `timeout-minutes: 35` on the new job (a cluster start on a shared runner varies more than a compose start, so the margin over the 25-minute estimate is 10 minutes). Budget, a planning estimate to be measured in Code Generation: tool download and cluster start 4 min, image builds 6, apply and rollout 3, flows in two browsers 4, accessibility scans 1, timing (120 loads in Chrome, report only) 5, header, token, log checks 2, total 25. If the measured total is over the limit, the limit and this budget are revised in the open in Code Generation, never silently. The job runs in parallel with the compose job, so the longer of the two sets the pipeline's time. |
| NFR1.8 | The images are the compose images, with the same size limit. | The images built into the cluster come from `packages/backend/Dockerfile` and `packages/guardrails-server/Dockerfile` unchanged; the job prints the app image's size and fails above the 550 MB limit of u5 NFR1.4. |
| NFR2.18 | Tests are written first, and the code u6 adds has at least 85% line coverage. (Team practice; inception NFR2.) | The code u6 adds that is not a manifest, a workflow or a document lives in the existing `packages/e2e` package as TypeScript modules under `src/` (tool and cluster checks, the target-cluster refusal, Secret creation, image-build calls, apply and wait, the port-forward and its process-id file, the manifest checks, the stop). They have unit tests with a faked `kubectl` and `minikube` that run without a cluster or Docker, and they are counted by the package's 85% floor. Excluded from the count, each with its reason: the `.mjs` entry files (a few lines that only call a module in `src/`). The package's threshold is never lowered; the `e2e-unit` job already runs it. The earlier floors (u1 to u5) stay as they are. |
| NFR2.19 | One command starts the whole sample on minikube with no other manual step (FR9.1). | From a clean checkout with Docker, `minikube` and `kubectl` installed, `yarn minikube:up` starts the minikube cluster if it is not running (Docker driver, 2 CPUs, 4 GB), builds the two images into it, creates the namespace and the Secret, applies `k8s/`, waits until every workload is ready, starts the port-forward, runs the readiness check and prints the address. After it, the upgrade plan of a seeded service loads in the browser at `http://localhost:7007` (the same check as FR8.1). A missing tool gives a plain message naming it and where to get it. Unit tests cover: tools present or missing, a not-running cluster started, the refusal on another context, first run creates the Secret and a second leaves it unchanged, a taken local port, a failed rollout printing the diagnosis. |
| NFR2.20 | The manifests are checked without running a cluster. | Unit tests read the YAML under `k8s/` (following the `kustomization.yaml` resource list, using the `yaml` package already in the workspace; no `kubectl` needed) and assert the properties named in NFR5.13 to NFR5.18 and these: the app starts only after the server and the database report ready (init steps or probes, chosen in NFR Design); every workload has readiness and liveness probes using the same routes as compose (`/.backstage/health/v1/readiness` for the app, an exec probe running `node packages/guardrails-server/dist/probe/healthcheck.js` for the server, as compose does, and `pg_isready` for PostgreSQL); the database has a persistent volume claim; the app's two base addresses are equal to `http://localhost:7007` and come from a ConfigMap; the settings use the same names as `compose.yaml` (`GUARDRAILS_SERVER_URL`, `GUARDRAILS_DEMO_SIGN_IN`, `APP_BASE_URL`, `BACKEND_BASE_URL`, `BACKEND_PORT`, `POSTGRES_*`, `GUARDRAILS_SEED`); the seed is the literal `20261106`; resource requests and limits are set and no larger than compose's limits. Any violation fails. |
| NFR2.21 | The pipeline gets one new job, and it is part of the required status. | Unit tests read `.github/workflows/ci.yml` and assert NFR5.21 and these: the new job `minikube-e2e` needs `app-image`, runs on `ubuntu-latest`, and is listed in `needs` of the final summary job `ci-ok`, which fails when it does not succeed (FR10.1); the workflow still runs on pull requests and on pushes to `main`. The file tests are part of the `packages/e2e` unit tests, which the existing `e2e-unit` job already runs without Docker or a cluster. |
| NFR2.22 | A failure can be diagnosed from the pipeline's output. | On any failure the live job prints `kubectl get pods,svc,pvc`, `kubectl describe` and the logs of each pod in the namespace, and uploads the browser report and traces as a build artifact kept for 7 days (the same as the compose job). |
| NFR2.23 | Starting, stopping and starting again is safe, and the commands say what they keep. | `yarn minikube:up` run twice leaves the sample working (apply is repeatable, the Secret and the data are kept, the forward is restarted); `yarn minikube:down` stops the port-forward and removes the sample's namespace, and says that the data in it is gone and that the minikube cluster itself is left running. The live job always starts from a removed namespace so its results do not depend on an earlier run. |
| NFR2.24 | The same end-to-end checks prove the same result on both runs. (FR9.1 pass condition: "the same check as FR8.1 succeeds".) | The live job runs the u5 end-to-end specs with their assertions unchanged. They already read `E2E_BASE_URL` (`http://localhost:7007` through the port-forward), and u6 adds exactly two switches, both defaulting to today's compose behavior: `E2E_TIMING_BLOCKING` (NFR1.5) and `E2E_STACK` (`compose` by default, `minikube` in the live job). `E2E_STACK` is needed because the one server-down flow (`flows.spec.ts`, a failed change that is retried) ends and restarts the guardrails server through `docker compose` and `docker kill` (`specs/support/stack.ts`), which cannot reach a pod. With `E2E_STACK=minikube` the same three calls (find the server, end it, start it and wait until it is healthy) are made with `kubectl` in the namespace `guardrails-sample`: the server's Deployment is scaled to zero and back to one, and the wait ends when its pod is ready. The command construction lives in a module under `src/` (counted by NFR2.18, unit tested with a faked `kubectl`: both stacks, an unknown value refused, a failed call named in the error), and `specs/support/stack.ts` only chooses between the two. Code Generation measures that the end happens within the plugin's 5-second probe-reuse window as it does under compose, and if not, adjusts the spec's wait for the minikube stack only and records it. The flows in Chrome and Firefox: the flows in Chrome and Firefox, the accessibility scans, the keyboard walkthrough, the header, token and append-only checks (NFR3.1 to NFR3.3, NFR4.1, NFR5.20). Any failure fails the job. |
| NFR3.5 | Accessibility and the screen-reader checklist are not re-opened. | The automated scans of NFR2.24 cover NFR3 on minikube; the manual screen-reader pass of u5 NFR3.4 is on the same application and is not repeated, and the README says so. |
| NFR4.3 | The browser support is the same. | The live job runs both browsers at the 1440 by 900 window of u5 NFR4.1 and prints their versions (NFR4.2). |
| NFR6.2 | Everything u6 adds is formatted and linted with Backstage's settings, enforced in CI. (Inception NFR6.) | The new modules are covered by the same Prettier check as the repository and by `backstage-cli package lint` through the existing `lint` and `typecheck` steps of `packages/e2e`; the YAML under `k8s/`, the workflow edit and the README section pass `prettier --check`. A violation fails the pull request. |
| NFR7.3 | The minikube run shows the same data every time and the same data as compose. (Inception NFR7.) | The live run reads the seeded data through the real stack and compares the counts and names with the committed catalog and the default data set of u1 (seed 20261106, written as the literal in the ConfigMap); a second run after a removed namespace gives the same upgrade plan for the same service, compared byte for byte. |
| NFR7.4 | The audit and changes tables start empty after the namespace is removed and the sample started again. | The live run reads the changes list and the audit log of every seeded service after a fresh start and finds both empty (the same check as u5 NFR7.2). |

## Technology Decisions

| ID | Area | Decision | Reason |
|---|---|---|---|
| NFR2.25 | Kubernetes files | Plain YAML with Kustomize, applied with `kubectl apply -k k8s/`; one `kustomization.yaml` at `k8s/` listing the namespace-scoped resources (Q1: A) | Kustomize is built into `kubectl`, so nothing extra is installed; the files stay readable by tests; overlays for a hosted environment can build on this base later without changing it. |
| NFR2.26 | Workloads | A Deployment each for the guardrails server and the app, and a StatefulSet with one persistent volume claim for PostgreSQL (the local default storage class of minikube); ClusterIP Services for all three | Mirrors the three compose services; the claim keeps data across a pod restart as the compose volume does. |
| NFR2.27 | Settings | One ConfigMap whose keys have the same names as the compose environment; the database login in a Secret created by the start script (NFR5.14) | The application reads the same names in both runs; nothing needs to change in u4 or u5. |
| NFR2.28 | Images | Built inside the cluster with `minikube image build` from the existing build files, tagged `guardrails-app:local` and `guardrails-server:local`, `imagePullPolicy: Never` | No registry, no push and no login (nothing deploys, team practice); the same files as compose. |
| NFR2.29 | PostgreSQL | The exact tag compose uses, the Alpine variant | One value in compose, the two plugin jobs and `k8s/` (NFR5.18). |
| NFR2.30 | Reaching the app | `kubectl port-forward` to `127.0.0.1:7007`, started and tracked by the start script with a process-id file (Q2: A) | The app's two base addresses stay `http://localhost:7007` and the origin check, the content policy and the end-to-end specs need no change. |
| NFR2.31 | Start command | A Node script (`.mjs`, like the compose scripts) behind `yarn minikube:up` and `yarn minikube:down`; no shell script | Works on macOS, Linux and Windows; the logic is unit tested (NFR2.18). |
| NFR2.32 | Cluster tools | `minikube` and `kubectl` at exact versions chosen in Code Generation by checking the release pages that day, downloaded in the job and checked against SHA-256 values (NFR5.18); Docker driver | The pipeline rule allows only GitHub's own actions, so a third-party setup action is not used. |
| NFR2.33 | Pipeline | The existing workflow, extended with the job `minikube-e2e` and its entry in `ci-ok`, and the file tests added to the `packages/e2e` unit tests that `e2e-unit` runs (Q3: B). The existing jobs stay as they are | The new job only adds. |
| NFR2.34 | Nothing deployed | No registry login, no push, no deploy job (NFR5.21); the only cluster ever touched is the local minikube one (NFR5.17) | Team practice: nothing deploys automatically. |

New packages: none. The manifests, the workflow edit and the TypeScript modules in `packages/e2e` use what is already in the workspace (`yaml`, Jest through Backstage's test runner, `@playwright/test`). The allow-list check of u5 NFR5.8 stays as it is; if Code Generation finds a package is needed, the list is edited in the same pull request.

## Hand-offs

From u5 and what u6 does with each: NFR1.1 (timing) becomes NFR1.5 (report only on minikube); NFR1.3 (job budget) becomes NFR1.7; NFR1.4 (image size) becomes NFR1.8; NFR2.1 (coverage) becomes NFR2.18; NFR2.2 (one command) becomes NFR2.19; NFR2.3 and NFR2.4 (file checks) become NFR2.20 and NFR2.21; NFR2.6 (diagnosis) becomes NFR2.22; NFR2.8 (stop and start) becomes NFR2.23; NFR3.1 to NFR3.3, NFR4.1 and the u5 security checks NFR5.6, NFR5.7 and NFR5.11 are reused with their assertions unchanged as NFR2.24 and NFR5.20; NFR5.1 to NFR5.5 and NFR5.9 become NFR5.13 to NFR5.19 and NFR5.21; NFR7.1 and NFR7.2 become NFR7.3 and NFR7.4. u6 changes no application code: it adds `k8s/`, modules and tests in `packages/e2e`, one job in `ci.yml` and a README section, and makes two additive, default-preserving edits to u5's end-to-end package (the `E2E_TIMING_BLOCKING` and `E2E_STACK` switches of NFR1.5 and NFR2.24), which supersede the u5 hand-off line that the specs are reused unchanged. To Code Generation and later stages: the exact versions of minikube and kubectl and the PostgreSQL tag (checked that day), the choice between init steps and probes for ordering, and the writable-directory arrangement for the app's static files are fixed in NFR Design and Code Generation.

## Alternatives Considered

| Choice | Alternative | Why not |
|---|---|---|
| Plain YAML with Kustomize (Q1: A) | A Helm chart (Q1: B); plain YAML applied one by one (Q1: C) | Helm needs another tool and a template language that a single-environment sample does not need; applying files one by one has no way to add a hosted overlay later. Kustomize was the person's choice. |
| Port-forward to `127.0.0.1:7007` (Q2: A) | NodePort with `minikube service` (Q2: B); the ingress add-on (Q2: C) | NodePort gives an address chosen by minikube, so the base addresses and the checks would change on every run; the ingress needs an add-on, a hosts-file entry and sometimes a tunnel. The port-forward keeps the one address every setting and check expects. |
| A blocking live job on every pull request (Q3: B) | Manifest tests only (Q3: A); an advisory live job (Q3: C) | A regression in the manifests would not fail a pull request; an advisory job is read late or never. The cost is one more job in parallel (NFR1.7). Chosen by the person. |
| Timing reported, not blocking, on minikube | The same blocking limit as compose | A cluster in a shared runner adds noise unrelated to the change; inception NFR1 is measured on the compose run, where it is blocking. |
| Images built into the cluster, never pulled | Pushing to a registry and pulling | A push would break the no-deploy rule and need a login. |
| A Node start script | A Makefile or a shell script | Not portable to Windows, and untestable with Jest. |
| No network policies | Policies that minikube's default network cannot enforce | A policy that is not enforced looks like protection and gives none; stated as an accepted risk (NFR5). |
